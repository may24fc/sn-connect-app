## Known Risks
- The termination comment is HR-sensitive free text: it is intentionally absent from the `employee_directory` view and from audit metadata. Do not add it to the view or exports. `GET /api/employees/[id]` returns `select('*')` to the employee and their manager, so that route now nulls it for anyone who is not an admin or super admin (covered by `tests/api/employee-detail-termination-reason.test.ts`). The employee can still read their own `employees` row directly through RLS; terminated people cannot sign in, but revisit if that changes.
- Pre-existing: the Active tab's search term is kept when switching to Former, where there is no search box, so the Former list can look filtered with no visible cause. Not changed here.
- Superseded: permanent delete no longer hard-deletes rows, so the ~112 NO ACTION foreign keys (to `users`, `employees`, `auth.users`) no longer block it.
- The personal-data delete list in `purge_directory_user` is explicit. New tables holding per-user personal data must be added to it, or they will survive a purge.
- Shared records kept on purge include tickets and their comments, company events, project documentation, and AI expenses, which the schema would otherwise have cascaded.
- Edit Termination Date is hidden for former entries with no employee record (e.g. accounts that never completed onboarding); they can still be restored or deleted.
