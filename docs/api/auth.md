# Auth API

> Audience: Developers

Authentication is handled by Supabase Auth with PKCE flow. The application uses session cookies (httpOnly) managed by `@supabase/ssr`. There are no custom JWT endpoints — Supabase handles token issuance and refresh automatically.

**Related hooks:** `AuthContext` (`apps/web/src/contexts/AuthContext.tsx`)  
**Related middleware:** `apps/web/src/middleware.ts`, `apps/web/src/lib/supabase/middleware.ts`

---

## Endpoints

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `GET` | `/auth/callback` | None | PKCE code exchange |
| `POST` | `/api/auth/signout` | Session | Sign out current user |

> **Note:** The callback route lives at `/auth/callback` (not `/api/auth/callback`) — it's a Next.js route handler under `apps/web/src/app/auth/callback/route.ts`.

---

## GET /auth/callback

Exchange a one-time PKCE authorization code for a session. This route is the redirect target after email confirmation or password reset.

### Query Parameters

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `code` | `string` | Yes | One-time PKCE authorization code from Supabase |
| `next` | `string` | No | Post-login redirect path (validated against allowlist) |

### Flow

```
1. User clicks email confirmation / password reset link
2. Supabase redirects to /auth/callback?code=xxx&next=/dashboard
3. Server exchanges code for session via supabase.auth.exchangeCodeForSession()
4. Session tokens written to httpOnly cookies by @supabase/ssr
5. User redirected to validated `next` path (default: /dashboard)
```

### Security

- **Open redirect prevention:** The `next` parameter is validated against an explicit allowlist via `validateRedirectTarget()` from `@/lib/auth/redirect-config`. Invalid targets default to `/dashboard`.
- **PKCE replay protection:** Codes are one-time use; replayed codes are rejected by Supabase.
- **Session security:** Tokens stored in httpOnly cookies, never accessible to client-side JavaScript.
- **Chunked JWT support:** Uses the `getAll`/`setAll` cookie pattern to handle large tokens split across multiple cookies.

### Error Responses

| Scenario | Redirect |
|----------|----------|
| Missing `code` parameter | `/login?error=missing_code` |
| Missing Supabase env config | `/login?error=config` |
| Code exchange failed | `/login?error=auth_callback` |

### Example

```bash
# This URL is generated by Supabase, not called directly
GET /auth/callback?code=abc123&next=/dashboard
# → Sets session cookies → Redirects to /dashboard
```

## POST /api/auth/signout

Sign out the current user and redirect to the login page.

### Authentication

Requires an active Supabase session (cookie-based).

### Request

No body required.

```bash
curl -X POST https://your-app.com/api/auth/signout \
  -H "Cookie: sb-access-token=..." \
  --max-redirs 0
```

### Response

**302 Redirect** to `/login`.

The redirect URL is built using `x-forwarded-proto` and `x-forwarded-host` headers when available (for reverse proxy support), otherwise falls back to `request.nextUrl.origin`.

### Behavior

1. Calls `supabase.auth.signOut()` — clears session on Supabase side
2. Session cookies are cleared by the Supabase client
3. User redirected to `/login`

## Login Flow (Client-Side)

> Login is not an API route — it's handled client-side by Supabase Auth.

```typescript
// apps/web/src/app/(auth)/login/page.tsx
import { createBrowserClient } from '@/lib/supabase/client';

const supabase = createBrowserClient();

// Email/password login
const { data, error } = await supabase.auth.signInWithPassword({
  email: 'user@example.com',
  password: 'password123',
});

// OAuth login (redirects to provider)
const { data, error } = await supabase.auth.signInWithOAuth({
  provider: 'google',
  options: {
    redirectTo: `${window.location.origin}/auth/callback`,
  },
});
```

## Signup Flow (Client-Side)

```typescript
const { data, error } = await supabase.auth.signUp({
  email: 'user@example.com',
  password: 'password123',
  options: {
    emailRedirectTo: `${window.location.origin}/auth/callback?next=/onboarding/setup`,
  },
});
// → User receives confirmation email → clicks link → /auth/callback exchanges code
```

## Password Reset Flow (Client-Side)

```typescript
// Step 1: Request reset
const { error } = await supabase.auth.resetPasswordForEmail(email, {
  redirectTo: `${window.location.origin}/auth/callback?next=/reset-password`,
});

// Step 2: User clicks email link → /auth/callback sets session → redirects to /reset-password

// Step 3: Update password (on /reset-password page)
const { error } = await supabase.auth.updateUser({
  password: 'new-password',
});
```

## Mock Authentication

When `NEXT_PUBLIC_ENABLE_MOCK_AUTH=true`, authentication bypasses Supabase entirely. The `AuthContext` provides mock sessions with these test accounts:

| Email | Password | UI Role |
|-------|----------|---------|
| `employee@test.com` | `password` | employee |
| `intern@test.com` | `password` | intern |
| `admin@test.com` | `password` | admin |
| `superadmin@test.com` | `password` | super_admin |

Mock auth is controlled by `apps/web/src/middleware.ts` — when enabled, the middleware skips Supabase session checks and allows all routes.
